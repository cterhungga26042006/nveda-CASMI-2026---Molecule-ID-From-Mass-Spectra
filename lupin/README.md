# Lupin — Spectrum-to-Candidate Ranking

## 1. Role and objective

This directory contains Lupin's contribution to the Enveda CASMI 2026
molecule-identification competition.

The goal is to rank candidate molecular structures against LC-MS/MS
spectra. The ranker scores spectrum–candidate pairs and orders candidate
SMILES so that the most likely structure appears first.

The intended team workflow is:

1. Jens generates database-based molecular candidates.
2. Richard develops de novo molecular candidates.
3. Lupin scores and ranks candidate structures.
4. The team combines candidate sources and prepares the final submission.

The shared candidate table format is:

```csv
molecule_id,candidate_smiles,score
```

## 2. Current model

The current best model is:

**V3 fixed — 200k candidate catalog, 800 boosting rounds**

- Model: XGBoost ranking model.
- Input: spectrum and candidate molecular features.
- Candidate filtering: precursor neutral-mass matching.
- Mass tolerance: 10 ppm.
- Molecular features: RDKit-based descriptors and candidate features.
- Spectrum features: extracted from MS/MS peak information.
- Aggregation: candidate scores are combined across spectra belonging
  to the same molecule.
- Output: up to 25 ranked candidates per molecule.

The V3 pair-generation pipeline also preserves groups that contain
only a positive candidate, avoiding the earlier issue where such
groups could be dropped.

## 5. Environment

The pipeline was developed on Windows using Python 3.12.

Create and activate a virtual environment from the repository root:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
```

Install the main dependencies:

```powershell
python -m pip install numpy pandas pyarrow rdkit xgboost
```

Check the environment:

```powershell
python -c "import numpy,pandas,pyarrow,rdkit,xgboost; print('Environment OK')"
```

The exact package versions used for a run should be recorded when
reproducing or publishing that run.

## 6. Required data and files

Competition data must be downloaded separately and must not be committed
to this repository.

Expected inputs:

```text
data/
    train.parquet
    test.parquet

outputs/
    val_structs.csv
```

Important: `val_structs.csv` is generated by the repository-level
`make_val.py` script. Run this script before `prepare_training.py`.

It creates three shared validation artifacts:

- `outputs/val_structs.csv`
- `outputs/val_spectra.parquet`
- `outputs/val_solution.csv`

The validation structures are selected from training data excluding
`ingest_lib == 'enveda-180'`, using `test_size=500` and
`random_state=0`. Up to three spectra are sampled per structure.

All generated intermediate files, feature caches, models, and reports
are stored under `outputs/`, which is excluded from Git.

## 7. Preprocessing and training workflow

Run commands from the repository root.

### Step 1 — Generate the shared validation split

```powershell
python .\make_val.py
```

This creates `outputs/val_structs.csv`, which is required by the
training-data preparation step. It also creates the validation spectra
and solution files.

### Step 2 — Prepare training data

```powershell
python .\lupin\prepare_training.py
```

Input:

- `data/train.parquet`
- `outputs/val_structs.csv`

Output:

- `outputs/clean_train.parquet`

This step filters out the designated validation structures.

### Step 3 — Create the structure-level split

```powershell
python .\lupin\create_validation_split.py
```

Outputs:

- `outputs/ranking_train.parquet`
- `outputs/ranking_valid.parquet`

The split uses a 20% validation fraction and random seed 42.
Structures are split by `inchikey14`, preventing the same structure
from appearing in both partitions.

### Step 4 — Build the training candidate catalog

```powershell
python .\lupin\build_candidate_catalog.py
```

Output:

- `outputs/train_candidate_catalog.parquet`

The script validates SMILES and checks molecular formulas with RDKit.

### Step 5 — Generate training pairs

```powershell
python .\lupin\build_training_pairs_v3.py --output outputs/training_pairs_v3_fixed.parquet
```

This generates positive and negative spectrum–candidate training pairs.

### Step 6 — Generate pair features

```powershell
python .\lupin\build_pair_features_batched_v3_fixed.py --split train
```

Output:

- `outputs/train_pair_features_v3_fixed.parquet`

For validation features, the feature builder also supports:

```powershell
python .\lupin\build_pair_features_batched_v3_fixed.py --split valid
```

The configured validation inputs must exist before running this step.

### Step 7 — Train the V3 ranker

```powershell
python .\lupin\train_ranker_v3_fixed_200k_800.py
```

The current model and feature schema are saved as:

- `outputs/lupin_ranker_v3_fixed_200k_800.json`
- `outputs/lupin_ranker_v3_fixed_200k_800_features.json`

Additional training reports and feature-importance outputs are saved
under `outputs/`.


```text
outputs/test_ranked_candidates_lupin_v3_200k_800.csv
```

The CSV contains:

```csv
molecule_id,candidate_smiles,score
```

Observed test inference results from the current run:

- 400 test molecules.
- 1,127 spectra.
- 112,439 candidate pairs.
- 0 spectra without candidates.
- 9,083 ranked output rows.
- Up to 25 candidates per molecule.

Scores are XGBoost ranking scores, not probabilities. A negative score
is valid and does not indicate an inference failure.

## 9. Important integration limitation

The current inference script loads:

`outputs/train_candidate_catalog.parquet`

This is Lupin's training-derived candidate catalog. It is not necessarily
the final combined candidate catalog from Jens and Richard.

For the final team pipeline, the ranker must be evaluated and run against
the agreed combined candidate set. The current test CSV should therefore
be treated as a Lupin pipeline result, not as proof that all team
candidate sources have been included.

## 10. Competition submission integration

The competition expects one row per `molecule_id` with up to 25
semicolon-separated SMILES guesses in the `smiles` column.

Lupin's output is a ranked candidate table with one candidate per row.
It must be converted into the competition submission format by the
team's final submission pipeline.

The official competition metric is MRR@25. Candidate deduplication,
SMILES validity, molecule coverage, and ranking order must be checked
before submission.

The final `submission.csv` must be generated in the required Kaggle
Notebook environment according to the competition rules.

## 11. Reproducibility notes

- Run scripts from the repository root unless otherwise stated.
- Do not commit competition data, generated Parquet files, model files,
  Kaggle credentials, or private datasets.
- Several scripts refuse to overwrite existing outputs or caches.
  Move or remove old generated files deliberately before rerunning.
- Preserve the exact model feature schema used during training when
  performing inference.
- Record package versions, input data versions, and model artifacts
  for each reproducible run.
- Do not interpret internal validation metrics as hidden-test scores.
